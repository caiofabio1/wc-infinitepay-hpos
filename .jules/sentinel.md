## 2024-03-01 - Webhook Secret Fail-Open and Rate Limit Order
**Vulnerability:** The webhook secret validation previously allowed requests through if the secret was unconfigured (fail-open for backward compatibility), which allowed forged payment confirmations. Additionally, rate limiting applied *before* secret validation, potentially blocking legitimate API requests from shared IPs (like InfinitePay) during brute-force attacks against the endpoint.
**Learning:** In a payment gateway webhook, a fail-open policy for secrets breaks the core trust boundary. Payment confirmation must be explicitly rejected if auth fails, as an unconfigured secret means anyone can mimic the API. Reordering validation so that authenticated requests bypass IP-based rate limiting prevents distributed Denial-of-Wallet attacks while ensuring legitimate traffic gets through.
**Prevention:** Always default to fail-closed (`return false`) for security controls, regardless of configuration status. Ensure webhook architecture processes lightweight cryptographic validation (like `hash_equals` on secrets) before broader controls like IP transient rate limits when the upstream provider uses shared IP addresses.
